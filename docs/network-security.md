# Мережевий захист застосунку

## Rate Limiting

Використовується ковзне вікно: для кожної пари «IP + тип маршруту»
зберігаються мітки часу запитів, старші за 60 секунд відкидаються.

| Маршрут | Ліміт | Вікно |
|---|---|---|
| вхід (`…/login`) | 5 запитів | 60 с |
| решта `/api/…` | 60 запитів | 60 с |

При перевищенні повертається `429` з `Retry-After` і кодом
`rate_limited`. Лічильники живуть у пам'яті процесу й очищуються після
перезапуску.

## WAF

Перевіряються шлях, query-параметри та тіло запиту:

| Сигнатура | Приклад |
|---|---|
| Path Traversal | `../../etc/passwd` |
| SQL Injection | `' OR '1'='1`, `UNION SELECT`, `exec xp_`, `DROP TABLE` |
| Command Injection | `cmd=/bin/sh`, `system(`, `| bash` |

При збігу сервер повертає `403` з кодом `waf_blocked` і додає IP у
Greylist на 5 хвилин. Наступні API-запити з цієї адреси отримують `403`
з кодом `ip_banned`.

XSS-текст WAF не блокує: він проходить серверну санітизацію з ЛР №3.
Це свідоме рішення, щоб не ламати збереження коментарів.

## Журнал

Події пишуться в консоль сервера:

```text
[WAF] IP 127.0.0.1 blocked: Path Traversal (/api/v1/user/profile)
[RATE LIMIT] IP 127.0.0.1 логін, retry 42s (/api/v1/accounts/login)
```

## Перевірка

```powershell
python manage.py
python tools/stress_check.py
```

Скрипт робить 10 спроб входу (очікувано `200` → `429`), потім запит із
Path Traversal (`403`), потім звичайний запит (`403`, бо IP у Greylist).

Після цього IP заблокований на 5 хвилин — перезапустіть сервер, щоб
скинути стан. Для скріншота журналу дивіться консоль сервера.

## Обмеження

Сигнатурний аналіз не виявляє нових атак і може давати хибні
спрацювання. Ліміт за IP блокує й користувачів за NAT/Proxy; у
промислових системах додають ліміти за користувачем і аномалії
поведінки. Словник лічильників варто обмежувати за розміром і
періодично чистити.
