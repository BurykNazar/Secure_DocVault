# Захист облікових даних

## Паролі

Пароль не зберігається у відкритому вигляді. Використовується bcrypt із
фактором трудомісткості 12: кожне хешування виконується навмисно
повільно, тому перебір на GPU стає економічно недоцільним.

Сіль генерує сам bcrypt для кожного запису. Вона зберігається разом із
хешем, тому два однакові паролі дають різні значення. Сіль не є
секретом: її призначення — унеможливити заздалегідь обчислені таблиці
та однакові хеші в межах бази.

Колонка `salt` у таблиці `users` містить службову копію солі з початку
хеша. Вона потрібна лише для наочності під час перевірки; сам хеш уже
містить сіль і без неї не перевіряється.

## Перевірка пароля

`bcrypt.checkpw` виконує порівняння сталого часу: функція не
зупиняється на першому розбіжному байті, тому час відповіді не
залежить від правильності префікса пароля.

Повідомлення про помилку однакове для невідомого користувача та
невірного пароля — «Невірне ім'я користувача або пароль».

## SQL-ін'єкції

Усі запити до бази — параметризовані:

```python
connection.execute(
    "SELECT id, username FROM users WHERE username = ?",
    (username,),
)
```

Текст SQL і дані передаються СУБД окремо, тому введення користувача
сприймається як літерал. Навіть рядок `' OR '1'='1` стає звичайним
ім'ям, якого немає в базі. Склеювання SQL із даними у проєкті відсутнє.

## Валідація

Пароль перевіряється на сервері: щонайменше 8 символів, велика й мала
літери, цифра, спеціальний символ, не більше 72 байтів. Ім'я
користувача — 3–30 символів із латиниці, цифр і «_». Пошта —
за регулярним виразом, без подвійних крапок.

## Токени доступу

Після успішного входу сервер видає пару підписаних JWT (HS256, ключ
256 біт): access-токен на 15 хвилин і refresh-токен на 7 діб. Кожен
токен має унікальний `jti`, тип (`access` або `refresh`) та час життя.

Захищений маршрут перевіряє заголовок `Authorization: Bearer <token>`.
Декодування виконується з жорстко заданим списком алгоритмів, тому
токен із `"alg": "none"` або підписаний іншим алгоритмом відхиляється
ще до аналізу даних. Підпис гарантує, що змінений вручну payload
(наприклад, підміна ролі на `admin`) не пройде перевірку.

Refresh-токен одноразовий: під час оновлення старий токен потрапляє до
списку відкликаних, а клієнт отримує нову пару. Повторне надсилання
старого токена трактується як replay-атака й повертає `401` з кодом
`token_reuse`.

## Що варто додати в наступних етапах

* захист клієнтської частини та заголовків відповіді;
* обмеження частоти запитів і сигнатурний фільтр;
* шифрування файлів сховища та електронний підпис.
