# Захист облікових даних

## Паролі

Пароль ніколи не зберігається у відкритому вигляді. Використовується
bcrypt із фактором трудомісткості 12: кожне хешування виконується
навмисно повільно, тому перебір на GPU стає економічно недоцільним.

Сіль генерує сам bcrypt для кожного запису. Вона зберігається разом
із хешем, тому два однакові паролі дають різні значення. Сіль не є
секретом: її призначення — унеможливити заздалегідь обчислені таблиці
та однакові хеші в межах бази.

Колонка `salt` у таблиці `users` містить службову копію солі з початку
хеша. Вона потрібна лише для наочності під час перевірки; сам хеш уже
містить сіль і без неї не перевіряється.

## Перевірка пароля

`bcrypt.checkpw` виконує порівняння сталого часу: функція не
зупиняється на першому розбіжному байті, тому час відповіді не
залежить від правильності префікса пароля.

Для неіснуючого користувача виконується «холоста» перевірка за
випадковим хешем. Це вирівнює час відповіді та заважає перелічувати
імена. Повідомлення про помилку також однакове: «Невірне ім'я
користувача або пароль».

## SQL-ін'єкції

Усі запити до бази — параметризовані:

```python
connection.execute(
    "SELECT id, username FROM users WHERE username = ?",
    (username,),
)
```

Текст SQL і дані передаються СУБД окремо, тому введення користувача
сприймається як літерал. Навіть рядок `' OR '1'='1` стає звичайним
ім'ям, якого немає в базі. Склеювання SQL із даними у проєкті відсутнє.

## Перебір пароля

Після п'яти невдалих спроб обліковий запис блокується на 15 хвилин.
Лічильник і час блокування зберігаються в базі, тому перезапуск
сервера не скасовує захист. Успішний вхід обнуляє лічильник.

## Журнал подій

`var/logs/access.log` містить JSON Lines із подіями:

* `account_created` — створено обліковий запис;
* `sign_in` — успішний вхід;
* `sign_in_rejected` — відмова (невідомий користувач, невірний пароль,
  неактивний запис);
* `account_blocked` — спрацювало блокування.

Кожен запис містить час, IP-адресу та ім'я користувача, тому інцидент
можна відтворити під час аудиту.

## Що ще варто додати в наступних етапах

* токени доступу замість повторного введення пароля;
* захист клієнтської частини та заголовків відповіді;
* обмеження частоти запитів і сигнатурний фільтр;
* шифрування файлів сховища та електронний підпис.
